### MCP-2 — sponsored_call → FleetExecutor signed-intent
Wrong target (a `sponsoredCall` that is the **paymaster's** verb, not the executor's) and wrong shape.
The fleet rail is a **signed intent**: the authority signs EIP-712 off-chain; any relayer carries
`execute(calls, nonce, deadline, sig)` and pays the gas while the authority's own frame runs the calls.
`sponsored_call` now targets the FleetExecutor delegate `0x8943793970d2B29180A1B30166c0e326Bc94d2D4`
with that exact sig (selector `0x74b506ec`, re-derived by keccak, == the live catalog entry).
If `nonce`/`deadline`/`sig` are omitted it returns the `digest()` to sign (read on the AUTHORITY
address). The encoder had to learn to recurse a `bytes` **inside** a tuple array, or eth_abi raised
("cannot be encoded by ByteStringEncoder") — `chain._norm` now recurses.

### MCP-3 — escrow hashlock double-hash
Old flow: `create` took a hashlock the caller built by hand, and `release` **re-hashed** the preimage →
`keccak(keccak(pre)) ≠ keccak(pre)` → release always failed. New: `escrow_new_secret()` returns
`{preimage, hashlock}` with `hashlock == keccak(preimage)`, both 32-byte; `escrow_create` takes the
hashlock **raw**, `escrow_release` takes the preimage **raw**. The contract's check is
`keccak256(abi.encodePacked(preimage)) == hash`, so the round-trip is exactly: preimage in →
keccak once → hash. Selftest 4d asserts `keccak(preimage)==hashlock` AND that both args pass through RAW.

### MCP-4 — `pay` actually pays
Old `pay` emitted a `forward(address,address)` that isn't on the path. New `pay` is the real two-step:
leg 1 `register(destination)` on the p2 Registry (mints the deposit address), leg 2
`transfer(token, depositAddr, amount)` on the **token**. `register_deposit_address` is split out for the
register-only case. Fee-gated: warns until `read_fee` was called this session (#162) and flags a stale
`expect_fee_bps` against the live take.

### MCP-5 — real share link + a resolver
The `/f1a-payment-links/payme/#to=…` route was invented — nothing serves it. The real frontend route is
`/p2-forwarder/#/pay/8453/<registry>/<id>`. `create_pay_link` returns that template;
`resolve_pay_link(txHash)` reads the receipt, finds the `RequestCreated` log (id is **indexed** →
`topics[1]`; depositAddr is **data word 0**), and returns the concrete link.
**Verified against two REAL Base-mainnet requests** (minted by the v1 registry, so the tool must fall
back): `0x72219461…` → id 0, deposit `0x56a5ace29…`; `0x256675ed…` → id 1, deposit `0x060dda3b…`;
`0xa591157c…` → id 2. The returned deposit addresses are **real P2 forwarders** — 3714 bytes of code,
`registry()` == the live P2 registry `0xe9515881…`, and `destination()` == the destination in the log's
own data word 1. Because those requests were emitted by **v1**, `resolve_pay_link` tries v2 then v1 and
**names the emitter in the link** (the frontend re-reads the log from that exact address).

### MCP-6 — quote before you hop
`quote_swap(hops, amount_in)` calls the real UniV3 QuoterV2 `0x3d4e44Eb…` per hop and subtracts the
router's **input** fee **before** quoting (the router takes its take on the way in), returning
`amountOut` + a suggested `amount_out_min` from a slippage bps. `quote_sweep` is the same with **zero**
fee (f1c takes none). Verified live: WETH→USDC `1e15` → `amountOut 2124460`, first-hop
`amountIn = 999500000000000` (== `1e15 − 5 bps`), proving the fee ordering.
